## 2026-09-16：Wiki 索引质量检查与信息框结构修复

### 今日目标

- 建立低成本的 Chroma 切块人工抽查方式。
- 分析“好吃哈奇”食谱切块缺少语义标题的问题。
- 保留 Wiki 信息框中的分组层级，使长内容切块后仍能理解上下文。

### 完成内容

1. 新增 `app/commands/sample_chunks.py`：
   - 默认从 Chroma 随机抽取 5 个切块。
   - 支持 `--count`、`--seed`、`--collection` 和 `--title`。
   - 在控制台输出 Chunk ID、完整 metadata 和正文。
   - 先读取候选 ID，再读取抽中的正文，不加载向量或 Embedding 模型。
2. 为随机抽样命令新增单元测试和 README 使用说明。
3. 通过随机抽样发现“好吃哈奇”食谱切块只有箭头关系，没有“食谱”标题。
4. 定位根因：
   - 原始 HTML 中“食谱”位于 `section.pi-group > .pi-header`。
   - 旧解析器只提取 `.pi-data`，忽略 `.pi-header`。
   - 整个变种信息框被合并成一个长章节，后续切块无法继承分组标题。
5. 修改 `app/rag/wiki_parser.py`：
   - 通用识别 portable infobox 的 `section.pi-group`。
   - 将“生存、繁殖、食谱、代谢、构成”等分组保留为独立语义章节。
   - 避免父级和子分组重复提取同一字段。
6. 新增回归测试，保证长食谱拆成多个块后，每个块都带有如下上下文：

```text
页面：好吃哈奇
章节：信息框 / 好吃哈奇 / 食谱
```

### 修改原因

RAG 检索到的单个切块必须能够独立理解。虽然 `A ➤ B` 可以帮助人判断转换关系，但如果切块没有“食谱”这个容器标题，检索器和生成模型就难以判断它属于食谱、代谢还是普通属性。保留 HTML 自带的语义标题比针对某个页面硬编码“食谱”更可靠，也能适用于其他小动物页面。

### 验证结果

- 随机抽样命令在当前 `langchain` collection 上执行成功。
- 修复前，“好吃哈奇”当前修订在 Chroma 中有 32 个旧切块。
- 使用新解析器离线解析后得到 40 个语义章节、47 个切块，其中“好吃哈奇 / 食谱”包含 4 个切块。
- 全量测试结果：`41 passed`，另有 2 条第三方依赖弃用警告。
- `git diff --check` 通过。

### 当前限制与待办

- Chroma 中仍然是旧的 32 个切块；本次只修复了解析和切块代码。
- 当前增量索引以 Wiki `revision_id` 判断是否需要更新。同一修订下修改解析器时，普通索引命令会跳过页面。
- 不能简单实现“先删旧切块再写新切块”的强制重建，否则 Embedding 失败时会失去旧索引。
- 下一步需要设计带回滚保护的同修订安全重建，再重新索引“好吃哈奇”。
- 食谱 HTML 使用网格布局，当前仍可能被压平成连续文本，单条食谱的行边界需要后续继续评估。

技术细节见 [Wiki 数据处理技术文档](./wiki-data-pipeline.md)。

## 2026-09-16：缺氧 Wiki 增量同步与版本化索引

### 完成内容

- 数据来源改为《缺氧》中文 Wiki，第一版范围为正文命名空间中的“建筑”和“小动物”分类及其递归子分类。
- 排除调试、未实装、未使用、已移除和开发者相关分类。
- 通过 MediaWiki API 发现页面和读取修订，不直接把网页抓取结果当作知识库正文。
- 实现 dry-run、新增/更新/未变化/下线增量计划和部分页面同步。
- 按 `page_id/revision_id.json` 保存不可变原始快照，同时保留 Wikitext 与 HTML。
- 新增 `wiki_sources`、`wiki_pages` 和 `wiki_sync_runs` 数据表。
- 实现 Wiki 信息框、正文标题层级和常见内容块解析。
- 实现按语义章节切块，以及按 Wiki 修订版本写入和替换 Chroma。
- 新增 `sync_wiki` 和 `index_wiki` 命令。
- 首批索引“电解器”“人力发电机”和“好吃哈奇”三个页面。

### 关键决策

- SQLite 保存页面、修订和索引状态，Chroma 保存切块、metadata 和向量。
- 原始快照与向量索引分成两个阶段，抓取成功不代表索引成功。
- 使用 `revision_id` 作为增量判断依据；新修订写入并校验成功后才删除旧修订切块。
- 切块 ID 使用 `wiki:{page_id}:{revision_id}:{chunk_index}`，便于幂等重试和按修订删除。

## 2026-09-13：第二阶段 FastAPI 工程化改造

### 完成内容

- 建立 `app/api`、`app/core`、`app/rag`、`app/services`、`app/schemas` 和 `app/models` 分层结构。
- 增加文档上传、查询、删除、独立检索、问答和健康检查接口。
- 使用 Pydantic 定义请求响应模型。
- 使用 SQLite 保存文档元数据，Chroma 继续保存切块和向量。
- 文档删除时同时删除 SQLite 元数据和对应 Chroma 切块。
- 将 PDF、DOCX、XLSX 和本地 HTML 的加载逻辑迁入 RAG 模块。
- 拆分解析、切块、向量化、检索、重排、上下文构造和答案生成边界。
- 增加统一异常结构、日志、Trace ID、CORS 和 Pytest 测试。
- 保留可独立调用的检索入口，为未来 Agent 工具化预留边界。

### 关键决策

- Chroma 不替代关系数据库：前者负责相似度检索，后者负责文档状态、目录信息和业务关系。
- Service 层负责业务流程编排，但可以包含跨存储的一致性顺序，例如先删除 Chroma 切块，再删除 SQLite 元数据。
- FastAPI 成为当前后端主入口；旧 Streamlit 入口暂时保留用于历史兼容，尚未删除。
